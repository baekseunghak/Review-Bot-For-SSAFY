## 1. 한 줄 요약

Mattermost 비공개 팀채널에서 나를 멘션한 글을 감시해, 리뷰 요청이면 glab으로 해당 MR을 특정하고 워크트리를 준비한 뒤 데스크톱 앱에 리뷰 세션을 띄운다.

## 3. 불확실 항목 a~f 판단

### a) 비공개 채널 감시 — **WebSocket + 내 계정 PAT. 봇 불필요.**

Outgoing webhook은 공개 채널 전용이라 애초에 후보가 아니다. 남는 선택지는 셋:

| 방식 | 비공개 채널 | 필요한 관리자 작업 | 판정 |
|---|---|---|---|
| **A1. 내 계정 PAT + WebSocket** | 내가 속한 모든 채널·DM | Integrations 토글 + 내 계정에 토큰 생성 권한 | **채택** |
| A2. 봇 계정 + 채널 초대 | 봇을 초대한 채널만 | 봇 생성 활성화 + 봇을 비공개 채널마다 초대 | 대안 |
| A3. `/users/login` 세션 토큰 | A1과 동일 | 없음 | 비권장 |

A1을 고르는 이유는 **내가 보는 것과 감시 범위가 정확히 일치**하기 때문이다. 봇은 비공개 채널마다 초대해야 하고, 초대되는 순간 그 채널의 모든 글을 봇이 읽게 되어 감시 범위가 필요 이상으로 넓어진다. A1은 새 신원을 만들지 않으므로 초대도, 범위 확대도 없다.

A3(비밀번호 로그인)는 비밀번호 보관이 필요하고 MFA에서 깨지므로 문서에만 남기고 구현하지 않는다.

**PAT가 조직 정책상 막혀 있으면** A2로 폴백한다. 이 경우 멘션 판정은 "MM이 알려주는 내 멘션"이 아니라 봇이 받은 글에서 `@내아이디` 문자열을 찾는 방식이 된다.

### b) glab 설치·로그인 — **설치는 안내만, 로그인은 자동화 불가. 사용은 가능.**

이 PC는 이미 설치·로그인이 끝나 있어 실질 작업은 **프리플라이트 점검**뿐이다.

- 설치 자동화는 하지 않는다. OS별 패키지 매니저(winget/scoop/brew/apt)를 호출하는 순간 플러그인이 시스템을 변경하게 되고, 실패 경우의 수가 설치 안내문보다 훨씬 많다. `glab --version` 실패 시 OS에 맞는 설치 명령 한 줄을 출력하는 선에서 끝낸다.
- 로그인은 **자동화하면 안 된다.** `glab auth login`은 브라우저 OAuth 또는 토큰 붙여넣기이고, 토큰은 사용자가 직접 입력해야 하는 자격증명이다. 플러그인은 `glab auth status` 출력을 파싱해 대상 호스트가 로그인돼 있는지만 확인하고, 아니면 `glab auth login --hostname <host>`를 안내한다.
- 사용은 문제없다. glab은 토큰을 OS keyring에 보관하므로 플러그인이 `glab`을 그냥 실행하면 인증이 따라온다. 별도 토큰 전달·저장이 필요 없다 — 이게 GitLab REST API를 직접 호출하지 않고 glab에 위임하는 가장 큰 이유다.
- **주의:** `glab auth status`는 일부 호스트가 실패해도 exit 0이다. 반드시 `Logged in to <host>` 문자열로 판정한다.

### c) 리뷰 여부 판단 → 라우팅 — **가능하고, 대부분 LLM 없이 끝난다.**

3단계로 나눠 비용이 낮은 순서로 판정한다.

1. **T0 (정규식, 무료):** 이 저장소의 `review-request` 컨벤션은 `<@멘션> :merge_please: !<번호> | [<지라키>] <메시지>` 한 줄 형식을 `src/core.js`에서 이미 강제하고 있다. 팀이 MMP로 리뷰를 요청하는 한 T0에서 100% 확정된다. `core.js`의 `REVIEW_TEXT_PATTERN`도 그대로 재사용한다.
2. **T1 (휴리스틱, 무료):** 컨벤션을 벗어난 글이라도 `!\d+` 또는 지라 키 패턴 + 리뷰 동사가 함께 있으면 리뷰로 본다.
3. **T2 (LLM):** 위에서 안 걸린 애매한 글만 감시 세션이 직접 판정한다. 이미 돌고 있는 Claude 세션이 처리하므로 프로세스가 늘지 않는다. 출력은 `review` / `not_review` 두 값만 허용한다.

라우팅 자체는 if/else다. `not_review`면 알림만 남기고 아무 작업도 하지 않는다 — 이게 중요하다. 판정이 애매할 때의 기본값은 "아무것도 안 함"이어야 하며, 잘못 리뷰를 띄우는 쪽으로 기울면 안 된다.

### d) 워크트리 생성 + 세션 오픈 — **가능. 단, 워크트리는 미리 만들고 세션이 들어가게 한다.**

- 워크트리: `git worktree add`로 감시 세션이 직접 만든다.
- MR 브랜치: `git fetch origin merge-requests/<iid>/head:mr-<iid>` 로 가져온다. `glab mr checkout`은 현재 작업트리를 바꾸는 명령이라 워크트리 방식과 맞지 않는다.
- 세션 진입: `EnterWorktree`는 `path` 인자로 **이미 `git worktree add`로 만든 워크트리에 진입하는 것을 공식 지원**한다(`git worktree list`에 있어야 함). 따라서 "미리 만들고 → 새 세션이 진입" 순서가 문서화된 경로다.
- 워크트리 기본 위치는 `<repo>/.claude/worktrees/mr-<iid>`로 둔다. 앱 자체 규약과 같아서 세션 종료 시 정리 흐름을 그대로 탄다. 사용자가 다른 폴더를 지정하면 그 값을 쓴다.

### e) 데스크톱 앱에 세션 표시 — **가능하지만 클릭 1회가 낀다. 이게 현재 확인된 유일한 경로다.**

확인된 것과 아닌 것을 구분한다.

- **확인됨:** `mcp__ccd_session__spawn_task`는 데스크톱 UI에 칩을 띄우고, 클릭 한 번으로 **자체 세션 + 새 워크트리**를 만든다. `cwd`로 다른 저장소 루트도 지정할 수 있다.
- **확인 안 됨:** 다른 도구들의 설명문이 `start_session` / `hand_off_to_session`이라는 **클릭 없이 세션을 만드는 도구**의 존재를 가리킨다(`open_session_in`, `detach_session`, `stop_session` 문서가 모두 언급). 그러나 **이 세션의 도구 목록에는 노출돼 있지 않다.** 사용자 빌드/설정에서 켜지면 즉시 e)의 정답이 되므로, 어댑터 한 겹을 두고 있으면 쓰고 없으면 `spawn_task`로 떨어지게 짠다.
- `claude --bg`로 만든 세션은 CLI 백그라운드 에이전트라 데스크톱 앱 세션 목록에 뜬다는 보장이 없다. 폴백으로도 쓰지 않는다.

**클릭 1회는 단점이 아니라 기능으로 본다.** 리뷰 요청은 남이 트리거하는 이벤트다. 사람 확인 없이 세션이 자동으로 열리면 f)의 대량 멘션 상황에서 통제가 안 된다.

### f) 대량 멘션 — **순차 큐. 병렬은 하지 않는다.**

- 감시기는 **적재만** 한다. 멘션 1건 = 큐 1행, `(channel_id, post_id)` 유니크로 중복 차단.
- 처리는 기본 동시성 1. 리뷰 작업은 네트워크(glab)와 디스크(워크트리)를 함께 쓰고, 같은 저장소에 동시에 `git fetch`가 겹치면 락 경합이 난다. 병렬로 얻을 게 없다.
- `spawn_task` 칩은 그 자체가 사람이 소비하는 큐다. 한 번에 최대 N개(기본 3)만 칩으로 띄우고, 나머지는 큐에 남긴 채 MM으로 "대기 M건" 한 줄만 보낸다.
- PC가 꺼져 있던 동안의 멘션은 **재생하지 않는다.** 부팅 시 밀린 20건이 한꺼번에 쏟아지는 게 놓치는 것보다 나쁘다. 마지막 확인 시각 이후 건수만 요약해 알린다.

## 4. 아키텍처

```
Mattermost (비공개 채널)
   │  WebSocket /api/v4/websocket  (내 PAT)
   ▼
[1] mm-watch.mjs          감시기: 멘션만 걸러 stdout에 JSON 1줄씩
   │  Monitor(command:) 로 세션에 이벤트 전달
   ▼
[2] 감시 세션 (데스크톱)   분류 T0/T1/T2 → glab 매칭 → 워크트리 준비
   │  spawn_task (칩 1개)
   ▼
[3] 리뷰 세션 (데스크톱)   EnterWorktree → MR 본문 + 최신 댓글 기반 리뷰
```

[1]은 의존성 없는 단일 파일이다. Node 24의 전역 `WebSocket`을 쓰므로 `package.json`은 그대로 둔다.

[2]가 데몬이 아니라 **세션**인 이유: `spawn_task` 같은 앱 도구는 데스크톱 세션 안에서만 호출된다. 별도 데몬을 두면 결국 세션에 일을 넘기는 IPC를 새로 만들어야 하는데, `Monitor`가 이미 그 역할을 한다.

## 5. 단계별 계획

### 5.0 선행 (10분)

```bash
git config --global --add safe.directory C:/work/reviewbot-mcp
```

현재 이 저장소는 소유자 불일치로 모든 git 명령이 실패한다. 자동화가 git을 돌리므로 먼저 풀어야 한다.

### 5.1 스파이크 (반나절) — 착수 전 반드시

계획 전체가 이 셋에 걸려 있다. 하나라도 실패하면 설계를 바꿔야 하므로 코드보다 먼저 확인한다.

1. **MM PAT 발급 가능 여부.** 계정 설정에 Personal Access Tokens 메뉴가 보이는가? 없으면 a)는 A2(봇)로 전환 — 채널 초대 절차가 추가되며 설정 UX가 통째로 달라진다.
2. **`merge-requests/<iid>/head` fetch 가능 여부.** `git fetch origin merge-requests/1/head:tmp-mr-1` 한 번. 막혀 있으면 source branch를 직접 fetch하는 방식으로 바꾼다(포크 MR은 포기).
3. **`posted` 이벤트에 `mentions` 필드가 실제로 오는가.** 오면 그걸 쓰고, 안 오면 `@내아이디` 문자열 매칭으로 간다. 둘 다 동작하므로 설계는 안 바뀌지만 필터 코드가 달라진다.

### 5.2 v0.3.0 beta — 감시 + 라우팅 (2~3일)

설계 문서: [beta-mr-review-watch-design.md](beta-mr-review-watch-design.md)

- `watch_targets` 테이블 + `watch_target_*` MCP 도구 4종
- `bin/mm-watch.mjs` 감시기
- `mattermost-review-watch` 스킬
- 프리플라이트(`glab`, `claude`, git safe.directory, 토큰)

### 5.3 v0.4.0 — 세션이 없어도 도는 상시화 (2일)

v0.3.0은 감시 세션이 열려 있어야 돈다. 상시화는 아래 순서로 올린다. **v0.3.0을 실제로 써 보기 전에는 착수하지 않는다** — 하루 멘션 3건짜리 문제에 데몬을 붙이는 건 과하다.

1. 멘션을 SQLite `review_jobs` 큐에 적재 (감시기가 직접 write)
2. `scheduled_task`(3분 주기)로 큐를 비우는 세션 실행
3. **선행 확인:** 스케줄 작업 실행은 unattended 세션이다. `send_message`·`detach_session`은 unattended에서 막혀 있다고 명시돼 있고, `spawn_task`는 명시가 없다. **`spawn_task`가 unattended에서 되는지 먼저 확인**하고, 안 되면 MM DM으로 "붙여넣기용 명령"을 보내는 방식으로 폴백한다.

### 5.4 하지 않을 것

- MR 리뷰 코멘트 자동 게시. 리뷰 초안까지만 만들고 게시는 사람이 한다.
- glab 설치 자동화 (b 참조)
- 병렬 리뷰 (f 참조)
- PC 꺼진 동안의 멘션 재생 (f 참조)
- GitLab REST API 직접 호출. glab이 인증까지 해결해 준다.

## 6. 위험

| 위험 | 대응 |
|---|---|
| MM PAT가 조직 정책상 금지 | 봇 계정(A2)로 폴백. 스파이크에서 먼저 확인 |
| PAT 유출 = 내 계정 전체 권한 | SQLite 아닌 OS 자격증명 저장소 사용, 로그·에러에 절대 미출력 (아래 설계문서 6절) |
| MR 매칭 오인 → 엉뚱한 코드 리뷰 | 후보가 정확히 1건일 때만 자동 진행. 0건·2건 이상은 사람에게 질문 |
| WS 연결이 조용히 끊김 | `hello` 미수신·핑 타임아웃 시 지수 백오프 재연결, 재연결 사실을 세션에 알림 |
| 워크트리 누적 | `mr-<iid>` 단일 이름 재사용, 리뷰 세션 종료 시 `ExitWorktree` |
