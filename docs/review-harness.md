# MR 리뷰 자동화 — 동작 원리

README의 기존 Claude Code 리뷰 흐름이 **무엇을 하는지**를 설명한다면, 이 문서는 **어떻게 강제하는지**를 설명합니다. 규칙을 바꾸거나 막힌 이유를 파고들 때 보세요. 새 MCP의 수신함 자동 처리와는 별도 흐름입니다.

현재 `prepare`에도 팀 프로필 1명 이상과 Jira Cloud 환경변수 4개가 필요합니다. 팀원이 0명이면 리뷰 준비와 주간 요약은 시작하지 않습니다. 등록 인원에 고정 상한은 없습니다. 처음 설정할 때는 [README](../README.md)의 등록·연결 순서를 먼저 따르세요. `.env`는 자동 로드하지 않으며 직접 CLI를 실행할 때도 Node `--env-file=<절대경로>` 또는 같은 프로세스 환경변수를 전달해야 합니다.

## 구성

| 파일 | 역할 |
|---|---|
| `bin/mr-review.mjs` | 리뷰 하네스. 단계를 상태 파일로 강제하고, PreToolUse 훅의 게이트도 겸한다 |
| `bin/mr-watch.mjs` | GitLab todos 폴러. 리뷰 요청을 한 줄 JSON 이벤트로 내보낸다 |
| `bin/bypass-review.mjs` | 승인 정책(`bypass` 켜짐/꺼짐)과 기본 채널을 저장한다 |
| `hooks/hooks.json` | `glab` 과 `node` 로 시작하는 Bash 명령을 게이트로 보낸다 |
| `skills/mr-review/SKILL.md` | 리뷰 절차 — 위험 지도, 빈틈 찾기, 필터, 심각도와 판정 기준 |
| `skills/mr-review/checklists/` | 언어별 점검 목록 (현재 Python). open-code-review에서 가져옴 |
| `skills/auto-review/SKILL.md` | 감시 절차 — 밀린 요청, 재무장, 칩 또는 인라인 리뷰 |
| `skills/bypass-review/SKILL.md` | 승인 정책 전환 |

스킬은 모델이 따르는 절차이고, 하네스와 훅은 모델이 절차를 어겨도 막히는 장치입니다. 판정 기준처럼 코드로 검사할 수 없는 것은 스킬에, 순서와 형식처럼 검사할 수 있는 것은 하네스에 둡니다.

## 리뷰 단계

상태는 리뷰가 일어나는 워크트리의 `<git-dir>/mmp-mr-review.json` 에 저장됩니다. 워크트리마다 독립이고 커밋되지 않습니다.

```
preparing → prepared → reviewed → posted → notified
```

| 단계 | 하는 일 | 강제 방식 |
|---|---|---|
| `prepare <MR링크> [--jira TEAM-1,TEAM-2]` | glab 로그인·프로젝트 일치·다른 리뷰 상태 확인 → 전용 워크트리 확보 → 등록 팀원 Jira 최신화·MR 관점 준비 → 최신 SHA·워크트리 일치 확인 → 본문·게시자 댓글·질문 반환 | 최신화 전에 `preparing`으로 무효화. 실패한 준비의 과거 맥락으로 다음 단계 진행 불가 |
| 리뷰 | diff 통독 → 위험 지도(변경 요약, severity 순 위험 목록, 위험별 확인 절차) → 위험 큰 것부터 담당자가 놓쳤을 빈틈을 코드로 검증 → 지적은 이 diff로 한정 | 스킬 |
| 필터 | 기록 직전, **코드가 틀렸다고 보여주는 지적만** 지운다. 확인하지 못한 지적은 지우지 않고 `[확인 필요]` 를 붙인다 | 스킬 |
| `record <approve\|hold> <본문파일> --memory-file <내부JSON>` | 판정·답글 본문과 구조화한 비공개 리뷰 기록 저장 | 필수 섹션·태그·인용·판정 일관성(아래 "판정 검사"), 새 준비의 메모리 구조·근거·현재 SHA 검사를 어기면 거부 |
| `post` | GitLab 최신 SHA 재확인 후 `glab mr note create --unique` 로 답글 게시 | `reviewed`가 아니거나 맥락이 없거나 커밋이 달라지면 거부. `bypass`가 아니면 `--confirmed` 필요 |
| `notify` | `review-complete` 컨벤션으로 MR 작성자에게 DM | `posted` 가 아니면 거부 |

### 필수 섹션

- 승인: `## 리뷰 결과: 승인`, `### 확인한 범위`
- 보류: `## 리뷰 결과: 보류`, `### 왜 보류인가`, `### 수정이 필요한 부분`, `### 확인한 범위`

팀 맥락을 포함해 새로 준비한 리뷰에는 `### 작업 맥락`과 실제 연결 Jira키·담당 영역·변경 경로 중 사용한 근거가 필요합니다. 개인별 전체 업무 원문이나 내부 저장 경로를 공개 댓글로 복사하지 않습니다.

### 비공개 리뷰 기록

새로 준비한 리뷰의 `record`에는 `--memory-file <내부JSON>`이 필요합니다. 이 파일은 공개 답글 본문과 별개이며 리뷰를 수행한 대화가 기존 MR 설명·댓글·코드·Jira·테스트 근거에서 작성합니다. MR 템플릿에 새 항목을 채우도록 요구하지 않습니다. 연결 Jira키는 기존 제목·설명·브랜치 또는 선택 `prepare --jira`에서 가져옵니다. 완료 기록에 임의 이슈를 덧붙이지 않으며 Jira키가 없으면 MR·SHA와 변경 파일 기준으로 누적합니다.

내부 JSON에는 `implementation`, `decisions`, `validations`, `remainingWork` 네 배열을 두며 정규화한 전체 메모리는 64KiB 이내입니다. 직접 확인한 `observed`, 출처의 진술인 `reported`, 미확인인 `unknown`을 구분하고 근거를 연결합니다. 결정 이유를 모르면 `reason: null`, 실행하지 않은 검증은 `not_run`으로 남깁니다. 기존 MR 설명은 준비 맥락에서, 댓글은 리뷰 대화나 CLI의 `authorNotes`에서 확인한 뒤 출처를 적습니다. 형식과 한도는 [팀 작업 맥락](TEAM-CONTEXT.md#리뷰-완료-기록과-재사용)을 따릅니다.

저장 직전에 준비한 맥락 버전과 GitLab의 현재 SHA를 확인합니다. 성공한 `record`의 `reviewed`는 비공개 로컬 기록 완료이며 Jira 완료·댓글 게시·GitLab 승인·머지를 뜻하지 않습니다. 다음 준비는 같은 MR·연결 Jira키·같은 호스트와 프로젝트의 정확히 같은 변경 파일에 해당하는 이전 기록을 최신 최대 10개·100,000 JSON 문자까지 자동 참고합니다. Jira키의 명시 연결은 다른 저장소에도 적용됩니다. 추가 기록은 `nextOffset`과 `review_history_list`로 확인합니다. 과거 SHA의 사실은 현재 코드와 다시 대조하고 남은 작업을 자동 해결 처리하지 않습니다.

### 판정 검사 (`verdictProblems`)

지적마다 심각도 태그(`[높음]` `[중간]` `[낮음]`)를 붙이고, 코드로 확인하지 못한 지적에는 `[확인 필요]` 를 붙입니다. 태그는 지적 항목의 첫 줄에만 씁니다. `record` 는 이 태그로 판정이 지적과 맞는지 봅니다.

| 검사 | 거부 조건 |
|---|---|
| 미확인 개수 | 제목이 `## 리뷰 결과: <판정> (미확인 N건)` 이 아니거나 N이 `[확인 필요]` 줄 수와 다름. 0건이면 괄호가 없어야 함 |
| 승인 | 확인된 `[높음]` 줄이 하나라도 있음 |
| 보류 | `### 수정이 필요한 부분` 에 **카테고리 태그와 코드 위치가 한 줄에 함께 있고 `[확인 필요]` 가 아닌** 줄이 하나도 없음 |

확인한 범위에 적힌 카테고리·인용은 보류 사유로 치지 않습니다. 보류 사유는 수정이 필요한 부분에만 있어야 합니다.

**하네스가 못 하는 것**: 모델이 확인하지 못한 것에 `[확인 필요]` 를 붙이지 않거나, 심각한 지적을 `[중간]` 으로 낮춰 적으면 잡지 못합니다. 그건 스킬의 "위험 지도의 high는 셋 중 하나로 닫혀야 한다"와 보호 대상 규칙이 막습니다.

### 필터가 지적을 지우는 기준

[open-code-review](https://github.com/alibaba/open-code-review)의 `review_filter_task` 를 따릅니다. 틀린 지적을 남기면 작성자가 몇 초 쓰고 끝나지만, 맞는 지적을 지우면 아무도 모르게 사라집니다. 그래서 기본값은 남기는 것이고, 지우는 근거는 둘뿐입니다.

- **근거 A** — 지적 대상 코드가 이 diff에 없다 (변경 안 된 줄, 삭제된 줄, 다른 파일)
- **근거 B** — 읽은 코드의 특정 줄이 지적의 핵심 주장과 정면으로 모순된다. 추론이 한 단계 넘게 필요하면 모순이 아니다

보호 대상(동작·호환성 변화, 동시성, 되돌릴 수 없는 데이터 변경)에 대한 지적은 필터가 지우지 않습니다.

필터는 **남길지**를 정하고, 판정은 **확인된 것으로만** 정합니다. 이 둘을 한 단계에서 섞으면 "의심되면 내린다"가 되어 판정이 승인 쪽으로 기웁니다 — 초기 구현이 그랬습니다.

### 심각도와 판정

| 지적 | 판정 |
|---|---|
| 확인된 `[높음]` | 보류 |
| 확인된 `[중간]` | "병합 후에 고쳐도 되는가?" — 아니오면 보류 |
| `[낮음]` | 승인 + 안내 |
| `[확인 필요]` | 막지 않음. 제목에 개수 |

보호 대상은 확인되면 `[높음]` 입니다. 그 변화가 MR의 목적이고, 본문·문서에 밝혀져 있고, 호출부가 함께 바뀌었으면 예외입니다.

동작·호환성 변화는 **소비자가 있을 때만** 보호 대상입니다. 바뀐 값을 비교·저장·전달하는 곳이 있으면 `[높음]`, 없음을 확인했으면 `[중간]`, 판가름하지 못했으면 `[높음] [확인 필요]` 입니다. 과거 리뷰 재현 실험에서, 기본 경로의 설정 지문이 바뀌었지만 그 지문을 쓰는 곳이 없던 사례(`[중간]` 이 타당)를 글자 그대로의 규칙이 `[높음]` 으로 과잉 보류할 수 있어 추가한 조건입니다.

### 테스트 실행 범위

리뷰어는 워크트리에서 테스트를 돌려 확인하지만, **공용 자원(이미 떠 있는 로컬·원격 DB, 큐, 공유 스토리지, 외부 API)에 쓰는 테스트는 돌리지 않습니다.** 테스트가 스스로 띄우고 지우는 임시 컨테이너·메모리 DB·임시 디렉터리는 괜찮습니다. 판단이 안 서면 돌리지 않고 `[확인 필요]` 로 남깁니다. 재현 실험에서 한 테스트가 `DATABASE_URL` 기본값 때문에 로컬 공용 DB에 붙어 임시 스키마를 만든 일이 있어 추가한 규칙입니다. 이건 스킬 규칙이라 하네스가 막지는 못합니다.

### 보류 카테고리

보류 항목에는 심각도 태그와 함께 아래 중 하나를 붙입니다. 심각도는 "얼마나 나쁜가", 카테고리는 "왜 병합을 막는가"입니다. 어디에도 안 들어가는 지적은 보류 사유가 아니라 승인 + 안내입니다.

| 태그 | 뜻 |
|---|---|
| `[정확성]` | 잘못된 동작 |
| `[안전]` | 보안·권한 |
| `[데이터]` | 데이터 손상·유실 |
| `[계약]` | API·스키마·문서 계약 위반 (문서 때문에 실제로 깨지는 경우 포함) |
| `[구현]` | MR이 주장한 기능이 구현되지 않음 |

코드 위치는 백틱으로 감싼 `파일.확장자` 또는 `파일.확장자:줄` 형태여야 합니다(`` `src/auth.js:42` ``). 위치를 댈 수 없으면 확인한 것이 아니므로 남의 병합을 막지 않습니다.

## 왜 권한 프롬프트가 아니라 AskUserQuestion 인가

훅의 `ask` 결정은 세션 권한 모드에 따라 사람에게 닿지 않습니다. auto 모드에서는 분류기가 대신 해소하고, 사용자가 앞서 "코멘트 남겨줘"라고 말했으면 그 발화가 승인으로 읽힙니다. 그래서 게시 승인을 권한 계층이 아니라 대화 계층(`AskUserQuestion`)에 두고, 하네스와 게이트는 그 증거인 `--confirmed` 를 요구합니다. `deny` 는 모드와 무관하게 확정적입니다.

## 게이트 규칙

`hooks/hooks.json` 이 `glab *` 과 `node *` Bash 명령을 `mr-review.mjs gate` 로 보냅니다. 명령 위치(문자열 시작, 또는 `;` `&` `|` `(` 줄바꿈 뒤)에 있는 호출만 봅니다 — 문자열 안에 예시로 적힌 명령까지 막으면 문서 작업이 막히기 때문입니다.

| 명령 | 결정 |
|---|---|
| GitLab 승인·머지 (`mr approve`, `mr merge`) | 상태와 무관하게 거부 |
| MR 코멘트 작성 (`mr note`, list 제외) | **이 저장소에서 리뷰가 진행 중일 때만** 거부. 리뷰 중이 아니면 우회할 하네스가 없으므로 통과 — 작성자가 자기 MR에 리뷰 요청 댓글을 다는 경우 |
| MR 코멘트 조회 (`mr note list`) | 통과 |
| 하네스 `prepare` · `status` · `reset` | 자동 승인 |
| 하네스 `record` | 상태가 있으면 자동 승인 |
| 하네스 `post` | 단계·중복·`--confirmed`(bypass 제외) 검사 후 승인 또는 거부 |
| 하네스 `notify` | `posted` 일 때만 자동 승인 |
| 셸 변수·별칭으로 부른 하네스 | 거부만 하고 자동 승인은 하지 않는다 (우리 하네스라고 확신할 수 없음) |

알려진 한계: 정규식은 heredoc 경계를 모릅니다. 커밋 메시지 본문의 한 줄이 승인·머지 명령으로 시작하면 명령으로 오인해 막습니다. 백틱으로 감싸거나 문장 중간에 두면 됩니다.

## 워크트리 규칙

기본 위치는 `<메인 저장소>/.claude/worktrees/mr-<iid>` 입니다(`--worktree-root` 로 변경).

- 지금 서 있는 곳이 연결된 워크트리이고 이미 그 MR 브랜치면 그 자리를 씁니다
- 연결된 워크트리지만 다른 브랜치로 작업 중이면 **갈아끼우지 않고** 전용 워크트리를 따로 만듭니다
- `--here` 는 "이 자리는 이 리뷰 전용으로 방금 만들어졌다"는 호출자의 보증입니다. 감시가 작업 칩을 띄울 때만 붙입니다. 워크트리 안에서 보면 빈 자리와 남이 작업 중인 자리가 똑같이 생겨서, 하네스는 스스로 구분할 수 없습니다
- 커밋되지 않은 변경이 있는 워크트리는 거부합니다
- 포크 MR이라 원격에 소스 브랜치가 없으면 `merge-requests/<iid>/head` 로 폴백합니다

세션은 워크트리가 새로 만들어지면 `EnterWorktree` 로 들어갑니다. `cd` 는 셸 한 줄에만 적용돼 데스크톱 앱에 보이지 않습니다. 감시(bypass) 경로는 리뷰가 끝나면 `ExitWorktree({action: "keep"})` 으로 나옵니다 — 리뷰는 커밋을 남기지 않아 `remove` 하면 워크트리가 사라집니다.

## 세션 제목

`prepare` 가 `sessionTitle`(`<작성자 이름>) !<번호> 리뷰`)을 돌려줍니다. 스킬은 바꾸기 전에 현재 제목을 읽어 두고, 리뷰가 끝나거나 도중에 그만두면 그 제목으로 되돌립니다. 읽은 제목이 이미 그 MR의 `sessionTitle` 이면(작업 칩으로 열린 리뷰 전용 세션) 되돌리지 않습니다.

## 감시기

`bin/mr-watch.mjs` 는 60초마다 `glab api todos?state=pending` 을 읽습니다. LLM이 붙지 않습니다.

| 판정 | `action_name` |
|---|---|
| 확정 — 판단 없이 리뷰 | `review_requested`, `approval_required` |
| 판단 필요 — 댓글 본문을 보고 결정 | `directly_addressed`, `mentioned` |
| 제외 | `assigned` 및 그 외 |

- `watch.json` 에 없는 프로젝트의 todo는 무시합니다
- 첫 실행 시각을 `since` 로 저장하고 그 이전 todo는 재생하지 않습니다
- 처리한 todo id는 `watch-state.json` 의 `seen` 에 최근 500개까지 둡니다. GitLab의 todo를 done 처리하지 않습니다 — 상대의 GitLab 상태를 바꾸는 일이기 때문입니다
- 같은 폴링 배치 안에서 한 MR에 여러 todo가 오면 하나로 합치고, 확정 액션을 남깁니다. 배치를 넘어선 중복은 합치지 않습니다 — 수정 후 재리뷰 요청은 별개 사건입니다
- MR에 답글을 달면 GitLab이 그 MR의 내 todo를 자동으로 done 으로 넘깁니다. 게시한 MR이 밀린 목록에서 사라지는 건 이 때문입니다
- `host` 가 설정에 없으면 `glab auth status` 에서 `Logged in to <호스트>` 가 정확히 하나일 때만 그것을 씁니다. `glab auth status` 는 다른 호스트가 401이어도 종료 코드 0이고 출력이 전부 stderr 라서, 종료 코드가 아니라 출력 문자열로 판정합니다

`Monitor` 는 최대 30분이라 스킬이 만료 때마다 재무장합니다. 재무장 횟수는 대화 맥락으로 세며, 컨텍스트가 압축되면 0부터 다시 셉니다.
