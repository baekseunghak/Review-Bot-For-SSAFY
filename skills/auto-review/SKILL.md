# MR 리뷰 요청 감시

GitLab **todos**를 주기적으로 읽어 리뷰 요청을 감지한다. Mattermost를 보지 않는다 — todos는 이미 있는 glab 인증으로 읽히고, `action_name` 필드가 "리뷰 요청인가"를 대신 판정해 주며, `target_url`이 그대로 `/mmp:mr-review`의 입력이 된다.

감지된 요청은 **작업 칩**으로 띄운다. 사용자가 클릭하면 그 MR 전용 리뷰 세션이 열린다.

## 0. 설정 확인

감시는 `~/.mmp/watch.json`에 등록된 프로젝트에 대해서만 돈다. 없으면 만들어야 한다.

```json
{
  "projects": {
    "group/sub/repo": {
      "workdir": "C:/work/repo",
      "jiraBaseUrl": "https://jira.example.com/browse"
    }
  }
}
```

- `host` 는 생략 가능하다. 비우면 `glab auth status` 가 로그인했다고 보고하는 호스트를 쓰는데, **정확히 하나일 때만** 그렇게 한다. 적혀 있으면 그쪽이 이긴다
- 호스트를 정하지 못하면 감시기가 거부한다. 넘어가면 glab 이 현재 폴더의 remote 로 추론해 조용히 gitlab.com 에 붙고 401이 난다
- `group/sub/repo` 는 GitLab 프로젝트 경로. MR URL의 `/-/merge_requests/` 앞부분이다
- `workdir` 는 그 프로젝트의 **로컬 클론 경로**. 리뷰 세션이 여기서 시작한다
- `workdir` 와 `jiraBaseUrl` 중 하나라도 없으면 감시기가 거부한다. 절반만 설정된 프로젝트는 존재할 수 없다

설정이 없거나 불완전하면 **사용자에게 값을 물어서 만들어라.** 경로를 추측하지 마라.

## 1. 밀린 요청부터 본다

감시는 켠 시점 이후만 본다. 그러니 **켜기 전에** 이미 쌓여 있는 것을 한 번 보여준다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/mr-watch.mjs" --pending
```

상태를 건드리지 않는 읽기다. 여기서 본 것이 나중에 이벤트로 또 오지는 않는다.

출력이 비어 있으면 "밀린 요청 없습니다" 한 줄로 끝내고 2단계로 간다. 있으면 **표로 보여준다** — 오래된 것이 위로:

| 요청자 | MR | 제목 | 언제 | 확정 |
|---|---|---|---|---|
| `authorName` | `!<iid>` | `title` | `createdAt` 을 "3일 전" 처럼 | `certain` 이 true면 리뷰 요청 확정, false면 멘션 |

그리고 **하나만 묻는다**: 이 중 지금 띄울 것이 있는지. 사용자가 고르면 3단계의 `spawn_task` 로 띄운다(3개 상한은 여기에도 적용된다). 고르지 않으면 띄우지 않는다 — 밀린 것은 사용자가 이미 알고 미룬 것일 수 있다. **임의로 전부 띄우지 마라.**

## 2. 감시 시작

```
Monitor({
  command: 'node "${CLAUDE_PLUGIN_ROOT}/bin/mr-watch.mjs"',
  timeout_ms: 1800000,
  description: "GitLab MR 리뷰 요청"
})
```

- 60초마다 `glab api todos?state=pending`을 읽는다. LLM이 붙지 않아 사실상 공짜다
- **첫 실행은 지금 쌓여 있는 pending을 전부 건너뛴다.** 오래된 todo가 수십 건 쏟아지는 게 놓치는 것보다 나쁘다. 감시를 켠 시점 이후에 생긴 것만 본다
- **`Monitor` 상한이 30분이라 6시간을 한 번에 걸 수 없다.** 만료 알림이 오면 **묻지 말고 즉시 같은 설정으로 재무장한다.** 이벤트 0건인 만료는 정상이므로 보고하지 않는다
- 재무장이 **기본 12회(=6시간)** 를 넘으면 그때 한 번만 묻는다: "<N>시간째 감시 중입니다. 계속할까요?" 답이 없으면 계속한다
- **호출에 시간이 붙어 오면 그 값을 쓴다.** `/mmp:auto-review 12시간`, `8시간만 봐줘`, `하루종일` 처럼 자연어로 온다. 30분 = 재무장 1회이므로 **시간 x 2** 가 횟수다(12시간 → 24회). "계속", "무한", "끌 때까지" 면 묻지 않고 계속 재무장한다
- 이 횟수는 대화 맥락으로 센다. 세션이 압축돼 카운트를 잃었으면 **다시 0부터 센다** — 확인 질문이 한 번 늦게 뜰 뿐이고, 감시가 끊기는 것보다 낫다

세션 제목을 `MR 리뷰 감시` 로 바꾼다 — 이 세션이 무엇을 하고 있는지 사이드바에서 바로 보이게, 그리고 리뷰가 끝난 뒤 돌아올 이름을 정해두기 위해서다. **바꾸기 전에 지금 제목을 기억해 둔다** — 감시를 멈추면 되돌린다.

```
get_session({ session_id: "self" })          // 이 제목을 기억해 둔다
set_session_title({ session_id: "self", title: "MR 리뷰 감시" })
```

시작했으면 사용자에게 한 줄로 알린다 — 어떤 프로젝트를 보는지, 그리고 **지금 승인 정책이 무엇인지**:

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/bypass-review.mjs" status
```

`bypass` 가 켜져 있으면 **칩을 만들지 않고 이 세션이 직접 리뷰해서, 사용자 확인 없이 MR에 답글을 달고 DM을 보낸다.** 감시를 시작하면서 그 사실을 반드시 말한다. 바꾸려면 `/mmp:bypass-review off`.

## 3. 이벤트 처리

이벤트는 한 줄 JSON으로 온다.

| 필드 | 쓰임 |
|---|---|
| `certain` | `true`면 리뷰 요청 확정. `false`면 판단 필요 |
| `action` | `review_requested`·`approval_required`(확정) / `directly_addressed`·`mentioned`(판단 필요) |
| `mrUrl` | `/mmp:mr-review`에 그대로 넘길 링크 |
| `authorName` | 요청자 실명. 칩 제목·보고에 쓴다 |
| `body` | 멘션 맥락. `certain: false`일 때 이걸로 판단한다 |
| `workdir` | 리뷰 세션을 띄울 저장소 루트 |

**`certain: true`** → 바로 4단계로 간다. 다시 판정하지 마라.

**`certain: false`** → `body`를 읽고 판단한다. 리뷰를 부탁하는 말이면 4단계로, 단순 질문·정보 공유·감사 인사면 **아무것도 하지 않는다.** 애매하면 하지 않는 쪽이다 — 놓친 요청은 사람이 다시 부르지만, 잘못 띄운 세션은 시간을 쓴다.

**`type: "watch_error"`** → 감시기가 실패한 것이다. 메시지를 사용자에게 그대로 보고하고 감시를 재무장한다. 조용히 넘어가지 마라.

## 4. 리뷰 진행

**여기서 갈린다.** 2단계에서 읽은 `bypass` 값으로 정한다.

### bypass 켜짐 — 클릭 없이 이 세션이 워크트리로 들어가 리뷰한다

칩을 만들지 마라. 사용자가 누를 것이 없어야 한다는 게 bypass의 뜻이다.

**1) 워크트리를 만든다.** `--here` 를 붙이지 않는다 — 감시 세션이 서 있는 자리는 리뷰 전용 자리가 아니다.

```bash
cd "<이벤트의 workdir>" && node "${CLAUDE_PLUGIN_ROOT}/bin/mr-review.mjs" prepare <이벤트의 mrUrl>
```

`prepare` 가 `<프로젝트>/.claude/worktrees/mr-<iid>` 에 워크트리를 만들고 그 경로를 `worktree.path` 로 준다.

**2) 그 워크트리로 실제로 들어간다.**

```
EnterWorktree({ path: "<worktree.path>" })
```

`cd` 로 때우지 마라. `cd` 는 셸 한 줄에만 적용돼서 데스크톱 앱에는 아무것도 보이지 않고, 사용자는 리뷰가 어디서 도는지 알 수 없다. `EnterWorktree` 는 세션 자체를 옮기므로 앱이 그 워크트리를 표시한다.

이 1~2단계는 `/mmp:mr-review` 0단계와 같은 일이다. **여기서 했으면 거기서 또 하지 마라** — `prepare` 를 두 번 부르면 이미 진행 중인 리뷰라며 거부당한다.

**들어가지 못할 수 있다.** `EnterWorktree` 는 현재 저장소(또는 그 안에 중첩된 저장소)의 워크트리만 받는다. 감시 세션이 그 프로젝트 바깥에 서 있으면 거부된다. 그때는 **멈추지 말고** 워크트리 절대경로를 기준으로 리뷰를 진행하되, 사용자에게 한 줄로 알린다: "감시 세션이 <프로젝트> 밖에 있어 워크트리로 이동하지 못했습니다. 경로 기준으로 리뷰합니다."

**3) 리뷰한다.** `/mmp:mr-review` 스킬의 1~5단계를 그대로 따른다. 게시 승인 질문(4절)과 채널 선택은 bypass가 면제하므로 멈추지 않는다.

**4) 끝나면 나오고, 제목을 되돌린다.**

```
ExitWorktree({ action: "keep" })
set_session_title({ session_id: "self", title: "MR 리뷰 감시" })
```

**반드시 `keep`.** 리뷰는 커밋을 남기지 않으므로 `remove` 하면 방금 만든 워크트리가 사라진다. 사용자가 나중에 열어보길 원해서 이 방식을 고른 것이다.

**제목은 `mr-review` 6단계가 이미 되돌린다**(0단계에서 적어둔 제목으로). 위 호출은 그게 어떤 이유로든 빠졌을 때를 위한 확인 사살이다 — 제목이 이미 `MR 리뷰 감시` 면 아무 일도 일어나지 않는다. 되돌아가지 않으면 사이드바에는 리뷰 중으로 보이면서 실제로는 감시만 하게 되고, 다음 MR 제목으로 또 덮이며 감시 세션이 영영 남의 이름을 달게 된다.

나온 뒤에야 다음 MR을 집는다 — 감시는 원래 자리에서 계속 돈다.

**한 번에 하나씩.** 리뷰하는 동안 도착한 이벤트는 순서대로 쌓아두고, 끝난 뒤 다음 것을 집는다. 워크트리에 들어가 있는 동안 또 들어갈 수 없고, 동시에 두 MR을 리뷰하면 하네스 상태가 엉킨다. 대기 건수는 리뷰를 마칠 때 한 줄로 알린다.

끝나면 무엇을 했는지 한 줄로 보고한다 — MR 번호, 승인/보류, 워크트리 경로.

### bypass 꺼짐 — 작업 칩으로 띄운다

```
spawn_task({
  cwd: "<이벤트의 workdir>",
  title: "<authorName>) !<iid> 리뷰",
  tldr: "<authorName> 님이 MR !<iid>의 리뷰어로 지정했습니다.",
  prompt: "/mmp:mr-review <이벤트의 mrUrl> --here"
})
```

- `cwd` 는 반드시 이벤트의 `workdir`을 쓴다. 다른 경로를 넣으면 엉뚱한 저장소에서 리뷰가 돈다
- **`--here` 를 반드시 붙인다.** `spawn_task` 는 `cwd` 아래에 이 작업 전용 워크트리를 새로 만들어 세션을 거기서 시작한다. 그 자리가 이 리뷰만을 위한 빈 자리라는 것은 **여기서만 확실히 안다** — 워크트리 안에서 보면 방금 만들어진 빈 자리와 사람이 작업 중인 자리가 똑같이 생겼다. `--here` 가 없으면 `mr-review` 가 안전을 택해 워크트리를 하나 더 만들고, `spawn_task` 가 만든 자리는 빈 채로 남는다
- 칩은 클릭해야 세션이 열린다. 그게 사람 확인 지점이다 — bypass가 꺼져 있을 때 이 지점이 존재한다

**한 번에 3개까지만 띄운다.** 사용자가 처리하지 않은 칩이 3개면 더 만들지 말고 대기시킨 뒤, 몇 건이 밀려 있는지 한 줄로 알린다. 리뷰는 순차로 하는 일이고, 칩이 열 개 쌓이면 아무것도 안 하게 된다.

## 감시 멈추기

사용자가 "감시 멈춰줘", "감시 꺼줘", "그만 봐" 처럼 말하면:

1. 감시 `Monitor` 를 `TaskStop` 으로 멈춘다. 재무장하지 않는다.
2. 리뷰가 진행 중이면 **그 리뷰를 먼저 끝낸다.** 게시 직전에 멈추면 워크트리와 상태 파일이 반쯤 남는다. 사용자가 리뷰까지 당장 그만두라고 하면 `mr-review.mjs reset` 으로 상태만 지우고, 워크트리에 들어가 있었다면 `ExitWorktree({ action: "keep" })` 로 나온다.
3. 세션 제목을 감시 시작 전에 기억해 둔 제목으로 되돌린다.
4. 한 줄로 보고한다 — 멈췄다는 것, 대기 중이던 요청이 있었다면 몇 건이었는지.

`/mmp:bypass-review` 는 감시를 멈추지 않는다. 승인 정책만 바꾼다.

## 절대 하지 않는 것

- **todo를 done 처리하지 마라.** GitLab 상태를 바꾸는 일이고, 중복 방지는 감시기가 로컬 `watch-state.json`으로 이미 한다
- 설정되지 않은 프로젝트의 todo를 처리하는 것. 감시기가 걸러내지만, 임의로 `watch.json`에 프로젝트를 추가하지도 마라
- `assigned` 액션을 리뷰 요청으로 취급하는 것. 담당자 지정은 보통 "네가 머지해라"다
- **bypass가 꺼져 있을 때** 감시 중 리뷰를 직접 진행하는 것. 그때 이 세션은 감시만 하고, 리뷰는 칩에서 열린 세션이 한다
- 첫 실행에서 밀린 백로그를 처리하는 것

## 문제가 생기면

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/mr-watch.mjs" --once
```

한 번만 돌고 끝난다. 설정 오류나 glab 인증 문제를 바로 확인할 수 있다. 상태를 처음부터 다시 하려면 `~/.mmp/watch-state.json`을 지운다 — 그러면 그 시점 이후 todo부터 다시 본다.
